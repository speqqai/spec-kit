# Check drift

Reconcile the codebase against a feature spec: read the spec's Requirements table and the child build steps under each requirement as the source of intent, mark genuinely-done work done, and append the remaining gap as new child steps for `implement-spec` to complete. The only writes land in the spec over Speqq MCP (status flips and appended child steps). This skill changes no application code, runs no git comparison, and assesses the present state of the working tree.

## Prerequisites

- Speqq MCP must be connected. If a Speqq call fails with a connection or authentication error, run `check-connection` first.
- A feature spec with a Requirements table whose requirements carry child build steps.

## Steps

1. **Resolve the workspace.** Call `list_workspaces` before any other Speqq call. One workspace: use it. Several: ask which. Every workspace-scoped call (`spec_list`, `queue_read`, `get_context`) takes that `workspace_id`; spec-scoped calls key off the resolved `spec_id`.
2. **Resolve the active spec.** Resolve in exactly this order and stop at the first rung that answers. Never read or write a local pointer file; the active spec is always derived from Speqq-side data plus the checkout.
   - **A queue item the user picked.** `queue_read` the workspace queue and use that item's `linked_document_id` as the spec. (Today `queue_read` returns the full queue; scoped queue reads are queued R2 app work.)
   - **The spec the user names.** There is no spec search over MCP: `spec_list` the workspace and filter titles client-side. Feature spec titles are commit-form (`feat: X`, `feat(scope): X`, `fix(scope): X`); match against those.
   - **The current git branch.** Call `spec_orient` with the `workspace_id` and the current git branch (`git branch --show-current`). It resolves the spec linked to the branch (the spec's own branch link first, then row branch links) and returns `matched_by: branch_row`. Use the `active_spec` it returns. A branch that matches nothing returns a normal empty result: fall through.
   - **Specs with status `building`.** Exactly one: confirm it with the user. Several: ask which.
   - **Otherwise ask.** Present a short workspace overview from `spec_list` (title, status, updated) and let the user choose.
3. **Read the spec, and stop on missing intent.** `spec_read` the resolved spec for its tab list, then read the Requirements table in full: every requirement row, its child build steps, and current statuses. Child steps a prior check-drift pass appended are existing intent and feed the dedup gate.
   - No Requirements tab: STOP and direct the user to `write-spec` for the product Requirements. No requirement carries child build steps: STOP and direct the user to `write-spec` for the build steps. Never invent intent, and never produce a partial assessment.
4. **Read the code and build the intent inventory.** Optionally call `get_context` for workspace and product context; if it is empty or missing, proceed from the spec and repo alone. Use your own file tools (read, grep, glob) on the actual working tree, not an indexed or external code graph. Bound the assessment to a code-scope map: the files and surfaces the child build steps name, plus a keyword search for the concepts each requirement describes. Do not infer scope beyond what the spec and its steps define. The exit is an intent inventory with one stable key per requirement and child step, plus a code-scope map naming the real files in scope.
5. **Assess each item, with evidence.** For each item in the intent inventory, inspect the code in scope and record exactly one verdict, each citing the file or surface observed:
   - **done** the behavior is present and observably satisfies the item. A requirement is done only when its acceptance holds (its child steps done and its behavior observable); a child step is done only when its Done-when condition holds in the code as it stands.
   - **partially met** work exists but does not fully satisfy the item. Name what exists, where, and precisely what is missing.
   - **unmet** the work is absent from the code entirely.
   - Never mark aspirationally: no verdict of done because a step should be finished, was claimed finished, or exists on a branch you have not read. If you did not see it in the code, it is not done.
6. **Classify and rank each gap.** Classify anything not fully done by type: `missing` (absent), `partial` (incomplete), `contradicts` (the code conflicts with stated intent or a repo standard; read the repo's own instruction and convention documents during grounding and treat them as governing constraints), or `unrequested` (code not called for by the spec, surfaced for awareness; check drift never deletes code, it appends a step to review, justify, or remove it). Assign severity: CRITICAL (violates a governing repo standard, or a `missing`/`contradicts` gap blocking a high-priority requirement's baseline behavior), HIGH (missing or partial on a core requirement or step), MEDIUM (partial on a secondary requirement, or an unjustified unrequested addition), LOW (polish and low-risk leftovers).
7. **Run the dedup gate.** Before drafting any new step, re-read the existing child steps and rows gathered earlier, including steps a prior check-drift pass appended. A gap already covered by an existing step, done or pending, gets no new step; the existing step is the work item. Only genuinely uncovered work becomes a new step.
8. **Report the delta and get a go-ahead.** Present a compact findings summary (a table of finding, gap type, severity, source requirement or step, and the evidence observed) plus counts: items checked, verdicts by kind, findings by gap type and severity, rows to flip, and child steps to append (or none). This is the checkpoint; get the user's go-ahead before any write. Zero findings means zero writes: skip the remaining steps, report converged with the counts of what was checked, and recommend proceeding to review.
9. **Flip genuinely-done rows.** All writes to the spec are strictly sequential: issue one call, wait for it to return, then the next. For each requirement or child-step row whose verdict is done, `cell_set` its `status` to `done`. Touch nothing else on the row (no description rewrites, no title edits). Rows already `done` stay untouched. Leave partially-met rows at their current status; their gap becomes an appended step.
10. **Append the gap as new child steps.** Order CRITICAL and HIGH first, contradictions before the rest. Each new step is a child row under the requirement it delivers, concrete in the `write-spec` step form (Changes, Surfaces with real paths from grounding, Depends on, Done when as observable behavior), and names its gap type.
    - **Add to an existing requirement:** one `row_create` per step with `row_type` `child`, `parent_id` the requirement's row id, `title`, `description`, and `status` (`todo`). Nesting is one level deep, so the step attaches to the requirement, not to another step.
    - **A gap that needs a brand-new requirement:** create the requirement parent first (`row_create` with `row_type` `parent`, or `row_create_batch` for several parents at once, capped at 50 top-level rows per call), then create each child step under it with `row_create` (`row_type` `child`, `parent_id`). `row_create_batch` only makes flat top-level rows: it ignores `parent_id` and `row_type` and sets no status, so it cannot create children.
11. **Leave spec status alone.** Spec status is derived by the app: the server rejects any status value sent to `spec_update` ("Spec status is derived by the app and cannot be set directly"). Read it as a signal; never try to write it. Row status flips are how check drift records progress.
12. **Report the outcome.** After the final write (or the converged verdict), report: the outcome (converged or gap appended) with the spec title and `spec_id`; counts (requirements and steps checked; verdicts by kind; findings by gap type and severity); writes (rows flipped to done, child steps appended and under which requirement, plus any interim mechanisms used, such as evidence recorded in text pending R2 field-write support); and the next step (run `implement-spec` to complete the appended steps; a follow-up check-drift pass should find fewer or no remaining items).

## FYI

- **Append-only, never rewrite.** Never rewrite, renumber, reorder, or delete finished rows, existing child steps, or existing requirements, including steps a prior check-drift pass appended. When the code already satisfies everything, write nothing at all and report converged.
- **Converged means zero writes.** Zero findings means no status churn and nothing appended, only a report of what was checked.
- **Zero local state.** This skill never creates or modifies any file on the user's machine (no pointer files, no notes files, no findings markdown). Assessment notes live in agent context only. Reading the working tree and running read-only git commands (`git branch --show-current`) is fine; check drift performs no git writes and changes no code.
- **Not a diff tool.** It assesses the present working tree, not git history or a branch comparison.
- **Sequential writes.** All writes to one spec are sequential, never parallel. Parallel writes to one spec collide and silently drop content.
- **Patch semantics.** `spec_markdown_tab_update` is PATCH-based: a `patches` array of `{old_str, new_str}` where each `old_str` must occur exactly once in the tab. There is no whole-document replace parameter, and an empty `old_str` only initializes an empty tab. The append-only contract means check drift never rewrites finished prose; new work is appended as child rows, not by editing any tab.
- **No spec search over MCP.** Discovery is `spec_list` plus client-side title and status filtering; branch resolution is `spec_orient`.
- **Fixed enums.** Spec status (`draft`/`in_review`/`rejected`/`approved`/`queued`/`building`/`released`) is app-derived and rejected by `spec_update`, which check drift reads but never sets. Row status (`new`/`backlog`/`todo`/`in_progress`/`done`/`cancelled`) is set via `cell_set`. Never invent a status value; an unmappable label belongs in description text.
- **Field writability.** `cell_set` writes exactly: `title`, `description`, `status`, `priority`, `review_status`, `area`, `delivery_status`, `branch` (a GitHub branch link by name; trunk and default branches are rejected) with `branch_repository` when several repos are connected, `linked_document_id`, and `custom_fields`. Rows also carry `work_started_at`, `work_completed_at`, `completed_commit_sha`, and `completed_commit_url`, but those fields have no MCP write path; never claim to have stamped them. To record a landing commit or timestamp as evidence, put it in the appended step text or a custom column via `custom_fields`, and label it interim pending the R2 field-write support.
- **Quality gate.** Run this in conversation before declaring done, never as a written checklist: every verdict cites evidence from a file actually read, and nothing is marked done aspirationally; no appended step duplicates an existing step (including steps a prior check-drift pass appended), and every appended child step traces to its requirement and gap type with real surfaces and an observable Done-when; nothing existing was rewritten, renumbered, reordered, or deleted, and a converged run wrote nothing; the delta was reported and agreed before the first write, and all writes were sequential; no file was created or modified on the user's machine.
