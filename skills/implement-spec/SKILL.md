# Implement a spec

Execute the build steps that `write-spec` wrote as child rows under each requirement, against the real working tree. The requirement rows and their child steps are the live progress ledger: row status flips replace checklist files and `[X]` markers, so there is no tasks file, no progress markdown, and no local pointer. Git branches and commits are the implementation work, and they are the only things this skill ever writes to the user's machine.

## Prerequisites

- Speqq MCP must be connected. If a Speqq call fails with a connection or authentication error, run `check-connection` first.
- A feature spec whose requirements carry child build steps, written by `write-spec`. This skill executes plans; it does not invent them.

## Steps

1. **Resolve the workspace.** Call `list_workspaces` before any other Speqq call. One workspace: use it. Several: ask which. Keep the `workspace_id` for every subsequent call.
2. **Resolve the active spec.** Resolve which spec to build from Speqq-side data alone, in exactly this order. Stop at the first rung that resolves. Never read or write a local pointer file.
   - **A queue item the user picked.** `queue_read` the workspace queue and use that item's `linked_document_id`. If the item links no spec, fall through and ask (the last rung); never guess.
   - **The spec the user names.** `spec_list` and filter titles client-side; there is no spec search over MCP. Ambiguous match: show the candidates and ask.
   - **The current git branch.** Call `spec_orient` with the `workspace_id` and the current git branch (`git branch --show-current`). It resolves the spec linked to the branch (the spec's own branch link first, then row branch links) and returns `matched_by: branch_row`. Use the `active_spec` it returns. A branch that matches nothing returns a normal empty result: fall through.
   - **Specs with status `building`.** One: propose it and confirm. Several: list them and ask.
   - **Otherwise ask.** Present a short workspace overview (spec titles and statuses from `spec_list`) and ask the user to choose.
3. **Read the spec, and stop if the requirements carry no build steps.** `spec_read` the resolved spec and read the Requirements table. If no requirement has child implementation steps to execute, STOP: tell the user this skill executes plans and does not invent them, and direct them to `write-spec` to write the build steps under the requirements. Do not improvise steps.
4. **Read the requirements, their steps, and the design.** Read the Requirements table in full: each requirement row and, under it, its child build steps, with every row's id, title, status, and branch value. Each child step carries Changes / Surfaces / Depends on / Done when in its description. Read the Overview page for architecture, contracts, and failure conventions. The parent/child structure is the step-to-requirement map: each child step is a row you flip as you work it, and its parent requirement is the row you flip when all its children are done.
5. **Ground in context and the repo.** `get_context` for optional product grounding; empty or missing, proceed from the repo alone. Read the working tree with your own file tools. Read the repo's instruction and convention documents wherever they live. Discover the validation gates from the repo itself: its manifest scripts, CI configuration, makefiles, contributor docs. The gates you run are the repo's own commands, never assumed and never invented.
6. **Check the worktree.** Run `git status`. If the tree is dirty, surface the exact state to the user and ask how to proceed before touching anything. Never stash, discard, or commit pre-existing changes without explicit instruction.
7. **Verify the plan is executable.** Check each child step's Surfaces against the tree as it exists now and the dependency order for forward references. If reality has drifted (surfaces gone, work already done, steps stale), stop and present the mismatch. Small drift: propose editing the affected child step (its description via `cell_set`) and apply it only with the user's approval. Large drift: direct the user to `check-drift` (or `write-spec`) to reconcile before executing.
8. **Settle the branch.** Derive the branch name from the commit-form spec title: `feat: user auth` becomes `feat/user-auth`, `fix(checkout): payment timeout` becomes `fix/checkout-payment-timeout`. Never a trunk name (main, master, dev, develop, release/*); the row branch link rejects them. If the matching branch already exists (a resumed run), reuse it instead of creating a second.
9. **Present the run and get a go-ahead.** Present the requirement order, the child steps under each, the gates that will run, and the rows that will flip. Get the user's go-ahead. Do not write to Speqq or create the branch before it.
10. **Do the start-of-run writes.** Sequential, in this order, each confirmed before the next:
    - **Branch.** `git checkout -b <branch>` from the agreed base (or check out the existing branch on a resumed run).
    - **Row branch links.** For each requirement row this run delivers, `cell_set` its `branch` to the branch name; pass `branch_repository` when several repositories are connected. This is what lets any later session resolve the spec from the branch alone through `spec_orient`. If the write is rejected because no GitHub repository is connected to the workspace, record the branch name instead as a final line appended to the row's existing description (read the current text first and carry it, since `description` replaces wholesale) and label it interim.
    - **Queue item.** If the run started from a queue item, `queue_update_item` its status to `in_progress`. Spec status is derived by the app (`spec_update` rejects status writes), so the queue item's status and the row flips are the live work signals.
    - `work_started_at` has no MCP write (see field writability in FYI); do not attempt to stamp it. State plainly in the run report that it is unset pending the R2 field-write support.
11. **Work the step loop.** Work requirement by requirement, completing each requirement's child steps before the next. Within a requirement, honor every Depends on; steps with no shared surfaces and no dependency may proceed together, but their row writes are still sequential. Steps touching the same files run strictly in order. For every child step:
    - **Flip in_progress first.** Before writing any code for a step, `cell_set` the child step's status to `in_progress`. The ledger leads the work, not the other way around.
    - **Do the work.** The narrowest change that satisfies the step's Changes on its named Surfaces, in the repo's own patterns and conventions. Follow the repo's test-first convention where it has one.
    - **Validate.** Run the gates the repo defines: the step-relevant ones after the change, the full set at the end of each requirement. A red gate blocks the step: fix and re-run until green. Never advance past a failure, and never flip a row `done` over a red gate.
    - **Commit.** Commit-form message scoped like the spec title. Capture the SHA.
    - **Flip the step done and record the commit.** When the step's code lands, `cell_set` the child step's status to `done` and record the SHA (mechanism in FYI). Only then start the next step.
    - **Close the requirement.** When every child step of a requirement is `done` and its acceptance holds, `cell_set` the parent requirement's status to `done`.
    - **Report.** One short progress note per step in conversation: step, what changed, gate result, commit SHA, rows flipped.
12. **Handle failure or interruption.** Halt a sequential run at the failing step: report the error with context, suggest next steps, and leave the ledger honest. Started-but-unfinished rows stay `in_progress`; nothing is flipped `done` speculatively. For steps running in parallel, finish and record the successes, then halt and report the failures. If the user approves extra work mid-run (a discovered gap), add it as a child step under the relevant requirement with a single `row_create` (`row_type` child, `parent_id` the requirement's row id, which accepts `status`) rather than silently widening a step. `row_create_batch` cannot help here: it only makes flat top-level rows, ignoring `parent_id` and `row_type`, so a child must go through `row_create`.
13. **Run the completion checkpoint.** When the requirements' steps are exhausted (or the user stops the run):
    - **Validate.** Run the repo's full gate set one final time. Confirm each executed step's Done when actually holds, and that the row statuses match reality: no row `done` whose behavior is not observable.
    - **Report.** Requirements and steps completed, commits with SHAs, rows flipped, gates run and their results, and every remaining row that is not `done`, with why.
    - **Checkpoint with the user; do not decide alone.** Spec status is not this skill's to set, so disposition happens on the rows and the queue item. Ask how to disposition remaining rows (leave, `todo`, `cancelled`) and apply via `cell_set`. If the run started from a queue item, propose `queue_update_item` to `done` and apply only on a yes. If the user wants a delivery stage recorded, set `delivery_status` (`code_complete`/`preview_ready`/`prod_launched`) via `cell_set`.
    - **State the interim gaps** left by missing writes: unset `work_started_at`/`completed_commit_sha` fields and any description-recorded SHAs or branch names, pending the R2 field-write support.

## FYI

- **Zero local state.** Never create a pointer file, notes file, progress file, or scratch markdown anywhere on the user's machine. Working notes (the step-to-requirement map, gate results, drift observations) live in conversation context only. The single exception is git work that is the implementation: branching, editing source, committing. That is the deliverable, not state.
- **Row field writability.** Via `cell_set` a row accepts: `status`, `title`, `description`, `priority`, `review_status`, `delivery_status`, `area`, `linked_document_id`, `branch` (+ `branch_repository`), and `custom_fields` keyed by visible column name. `work_started_at`, `work_completed_at`, `completed_commit_sha`, and `completed_commit_url` exist on rows but have no MCP write today; the app populates them from its repository integration. Never attempt to set them and never fabricate their values.
- **Interim for the commit SHA.** Read the row's current description, then `cell_set` `description` to the existing text plus a final line `Completed in commit <sha>` (`description` replaces wholesale, so always carry the prior text). A spec may instead carry a visible commit column; if one exists, write the SHA there via `custom_fields`. Both are interim pending the R2 field-write support; say so in the run report so the gap stays visible.
- **Sequential writes.** All spec, tab, and row writes to one spec are strictly sequential: issue one call, wait for it to return, then the next. Parallel writes to one spec collide and silently drop.
- **Patch semantics.** `spec_markdown_tab_update` takes a `patches` array of `{old_str, new_str}` edits; each `old_str` must occur exactly once in the tab. There is no whole-content parameter; even a full rewrite is expressed as patches. An empty `old_str` only initializes an empty tab. Pure additions at the end use `spec_markdown_tab_append`. This skill patches a page tab, such as the Overview, only for a user-approved amendment, never to track progress; the child steps and their requirements are the progress ledger.
- **No spec search over MCP.** Discovery is `spec_list` plus client-side title and status filtering; branch resolution is `spec_orient`.
- **Fixed enums.** Spec status (`draft`/`in_review`/`rejected`/`approved`/`queued`/`building`/`released`) is derived by the app; `spec_update` rejects any status value. Read it as a resolution signal; never try to set it. Row status (`new`/`backlog`/`todo`/`in_progress`/`done`/`cancelled`) is set via `cell_set`. Never invent a value; an unmappable label belongs in description text.
- **Commit-form titles.** Spec titles are `feat: X`, `feat(scope): X`, or `fix(scope): X`; the branch name derives from them and is never a trunk name.
- **Working notes stay in context.** Grounding, the step-to-requirement map, and drift notes never land in the spec and never touch the user's disk.
- **Quality checklist.** Verify before declaring done, in conversation: the active spec was resolved by the ladder, in order, with zero local state, and no pointer or notes file exists anywhere; the run stopped at the start if the requirements carried no child build steps, and on a dirty worktree until the user answered; the branch derives from the commit-form spec title, is not a trunk name, and is linked on every delivered requirement row (or recorded interim with a label); the queue item went `in_progress` at start (spec status was never set by this run), every row flip used a real enum value, and every `done` flip happened before work moved on and carries its commit record; every gate run was a command discovered in this repo, and no step advanced past a red gate; all Speqq writes were sequential, and page tabs were patched only for user-approved amendments; the completion checkpoint asked the user before any final status write, and the interim gaps were stated, not hidden.
